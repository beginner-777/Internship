# TRACE AI

TRACE AI is an AI incident investigation workspace for developers, SREs, support engineers, and technical incident teams. It converts untrusted logs, alerts, deployment notes, and human observations into a structured, evidence-bound investigation. It is intentionally not a chatbot.

## What it does

- Secure incident intake with Zod and React Hook Form validation
- Local detection and optional redaction of API keys, bearer tokens, emails, private-key headers, and password assignments
- Server-only Gemini Interactions API integration through `POST /api/analyze`
- Structured JSON generation and second-pass Zod validation
- One controlled schema-repair retry
- Incident severity, customer impact, confidence, services, relationships, timeline, hypotheses, actions, healthy signals, evidence gaps, and limitations
- Timeline filtering by severity, service, and text
- Event-density visualization derived only from supplied events
- Interactive service relationship field with an accessible text/list alternative
- Copyable and print-ready investigation report
- Local persistence of the latest investigation and editor draft
- Explicit Demo Analysis when the API key is absent
- Explicit **Basic local analysis — not an AI analysis** fallback
- Responsive sidebar/mobile drawer, command palette, focus management, and reduced-motion support
- Lazy-loaded, device-aware React Three Fiber signal environments with CSS and WebGL fallbacks

## Technology

Next.js 16 App Router, strict TypeScript, Tailwind CSS 4, Framer Motion, React Three Fiber, Three.js, `@google/genai`, Gemini Interactions API, Zod 4, React Hook Form, Lucide React, Vitest, React Testing Library, Playwright, and axe-core.

## Architecture

```text
Browser
  ├─ Landing / workspace / investigation / methodology
  ├─ Local secret preflight and optional redaction
  ├─ Draft + latest investigation in localStorage
  └─ POST /api/analyze
       ├─ per-IP rate limit (5/minute)
       ├─ control-character removal + Zod request validation
       ├─ missing key → labelled Demo Analysis
       └─ Gemini Interactions API
            ├─ untrusted-evidence system boundary
            ├─ JSON Schema structured response
            ├─ 25-second timeout
            └─ Zod validation + one repair retry
```

No API key is imported by a client component. There is no Express server, database, authentication, or browser-side Gemini call.

## Gemini integration and prompt strategy

The server uses the official `@google/genai` SDK and `ai.interactions.create()` with `GEMINI_MODEL`. The system instruction treats the incident package as untrusted data, ignores embedded commands, forbids invented evidence or executed-action claims, and requires hypotheses to remain provisional. The response format uses JSON Schema generated from the Zod domain schema. The returned JSON is parsed and validated again; malformed output receives one fresh, controlled repair request before a normalized error is returned.

## Security and privacy

- `GEMINI_API_KEY` is server-only and never uses a `NEXT_PUBLIC_` prefix.
- Total incident content is limited to approximately 15,000 characters.
- Dangerous control characters are removed server-side.
- Complete evidence and keys are never intentionally logged.
- Errors use normalized codes and never expose stack traces.
- Requests are limited to five analyses per IP per minute in the active runtime instance.
- CSP, framing protection, MIME sniffing protection, referrer policy, and permissions policy are configured.
- Logs and notes are treated as evidence, never model instructions.

The in-memory rate limit is intentionally basic and instance-local. A distributed production deployment that needs global enforcement should use an external rate-limit store without storing incident evidence.

## Environment

Copy the example and add a Gemini API key only to the server environment:

```bash
cp .env.example .env.local
```

```env
GEMINI_API_KEY=
GEMINI_MODEL=gemini-3.6-flash
```

With no key, the server returns a clearly labelled Demo Analysis generated by the local rule engine. It is never labelled as live Gemini output.

## Production build and Vercel deployment

1. Push the project without `.env.local`.
2. Import it into Vercel as a Next.js project.
3. Add `GEMINI_API_KEY` and `GEMINI_MODEL=gemini-3.6-flash` to the Production and Preview server environments.
4. Deploy and verify `/api/health` returns `status: ok`.
5. Run the deployment checks in `docs/DEPLOYMENT_CHECKLIST.md`.

No separate server or build override is required.

## Limitations

- AI analysis quality depends on evidence quality and completeness.
- A confidence score describes evidence strength; it is not a causal probability.
- The server cannot verify that a recommended operational action was executed.
- The local fallback is pattern based and cannot understand full system semantics.
- localStorage persistence is device/browser specific and has no account sync.
- In-memory rate limiting is not shared across serverless instances.
- WebGL is optional; the service map and every workflow remain usable without it.

## Troubleshooting

- **Demo Analysis appears:** configure `GEMINI_API_KEY` in the server environment and restart.
- **Authentication failure:** replace the server-side key and verify its Gemini API access; never paste it into source.
- **Rate limited:** wait one minute or inspect upstream Gemini quota.
- **Timeout:** retry with a smaller, more focused incident package or use local analysis.
- **Invalid structured response:** retry once; if it persists, check model availability and the server schema.
- **Blank/failed 3D scene:** the CSS fallback should appear automatically. Disable graphics acceleration only if the browser itself is unstable.
- **Corrupted saved result:** return to the editor and run a new investigation; invalid local data is rejected.

## Rollback

Redeploy the last known-good Vercel deployment, verify `/api/health`, then smoke-test the sample incident. Environment variables are managed separately from source rollback. Full operational guidance is in `docs/OPERATIONS_AND_ROLLBACK.md`.
